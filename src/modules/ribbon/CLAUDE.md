# modules/ribbon/

> L2 | 父级: ../../CLAUDE.md

左侧边栏模块。它和 appearance 一样不生产笔记、不报 VaultSeed，在开荒流程里完全缺席；它管的是另一件事：ziminOS 那二十三条命令，哪几条该变成最左边那一列图标。

它存在的理由是一个很朴素的观察：命令面板对零基础学员是隐形的。学员知道「记灵感」这件事，却未必记得住 `Ctrl+P` 再打三个字；而一条命令只要点不到，它在产品里就等于不存在。社区插件 Commander 解决的正是这个问题，本模块把那件事收进 ziminOS 自身——不为多一个依赖，而是因为图标要与命令同源：命令改了名、换了图标，边栏上那个按钮必须当场跟着变，插件之间做不到这件事。

## 成员清单

icons.ts: 素材层，全仓库唯一存放图形的地方。二十四个图形出自同一套画法（Pikaicons：24 格、2 宽描边、圆头圆角），十六个是免费集里的原图，八个照同一套画法补画——暂停、播放、灯泡、调色板、对齐、循环在免费集里没有，四分之一饼必须与兄弟图标成套才讲得清「季」，dock（带左栏的面板）则根本不属于任何命令：它是设置页「边栏」标签页的图标，名字照样登记在 COMMAND_ICONS，图形照样住在这里。补画的一律复用原图的几何原语（半径 9 的圆、日历框），这样它们与原图并排时看不出接缝，而不是「像但不是」。三处技术决定值得记：其一，addIcon 把内容塞进一个 `0 0 100 100` 的外层 svg，这里再套一层自带 `0 0 24 24` 的内层 svg 把 24 格铺满，而不是把每个坐标乘以 4.1667——path 里的数字是设计稿上的数字，换算过一遍就再也改不动了；其二，描边宽度取 `var(--icon-stroke, 2)` 而非写死，ziminOS 恰好随库交付 Minimal + Style Settings，学员在外观面板里把图标调细时，只有我们这二十四个不跟着变的话，那列图标会一眼看出是外来户；其三，注册时同步登记 `removeIcon` 的卸载回调——图标库是 Obsidian 全局的，它不会随插件卸载自己清，这是本模块唯一的全局副作用，也因此是唯一需要手写清理的地方。
dock.ts: 呈现层，边栏上那一列图标。每枚按钮按命令分组着功能色（色表住在 core/commands 的 GROUP_COLORS）：同一套画法的笔画图标排成一列时形状要凑近才认得出，颜色隔着半个屏幕就分了组。它不认识任何一条具体命令——清单来自 ctx.commands 的花名册，因此加一条命令只要它经注册台注册过，就自动出现在边栏的可选清单里，本文件一个字都不用改。按钮按下去直接调花名册上的回调，不去问 Obsidian「id 为 X 的命令是谁」：那条路（executeCommandById）不在 obsidian.d.ts 里，为了摆几个图标再开一个非公开 API 的口子不划算，而回调本来就在手上。

## 只为勾上的命令建按钮

边栏只建勾选中的那几个按钮，而不是一次建齐二十三个再切显隐。这是本模块唯一需要解释的取舍，而且它的第一版是错的，值得把两次判断都记下来。

**第一版（错的）**：一次建齐二十三个，勾选只切 `el.toggle()`。当时的理由是「Obsidian 没有公开的『撤下某一个边栏按钮』，手动摘元素会留下悬挂记录」。真机核对推翻了它：`WorkspaceRibbon.onChange()` 会遍历它自己那份 `items`，对每一项无条件执行 `buttonEl.toggle(!item.hidden)`。也就是说 **inline 的 display 是 Obsidian 保留给自己的通道**，而 `item.hidden` 只有它自己的边栏菜单能改、公开 API 里没有入口。后果是硬的：第二次启动、装任何一个也调 `addRibbonIcon` 的插件、用户在边栏上右键或拖一下——任何一次 `onChange` 都会把二十三个图标全放出来，而设置页还显示着「已摆出 7 条」。

**第二版（现在这版）**，两条纪律：

其一，**只为勾上的命令调 `addRibbonIcon`**。这不只是修上面那个 bug，更是修一个 DOM 层面永远修不好的问题：手机端底栏的边栏菜单、桌面「设置 → 外观 → 功能区 → 管理」那个弹窗，都是遍历 `leftRibbon.items` 画出来的，只看 `item.hidden`，根本不看 DOM。一次建齐的话，那两处永远列着全部二十三条，包括「初始化笔记库」这种一辈子只该按一次的——那正是这个功能想消灭的杂乱。

其二，**本次会话内取消勾选的，靠 class 藏起来**（`.ziminos-ribbon-hidden`，styles.css 里唯一一条 `!important`，理由写在它自己头上）。发出去的按钮收不回来，所以只能先藏着；它在 `items` 里的那条记录要等下次重载才消失——重载时它压根不会被建出来。用 class 而不是 inline display，正是为了不站在 Obsidian 那条通道上：它清掉 inline display 之后，class 规则照样生效。

这个残留在桌面上无伤（边栏那一列是主入口，用户看到的就是消失了），在手机上却是零反馈——手机根本没有那一列（`.is-phone .side-dock-ribbon` 是 `display:none`），唯一入口是底栏菜单，而它读 items 不读 DOM。所以手机端取消勾选时弹一句提示，这是全模块唯一一处 Notice。

还有一把锁不归我们：Obsidian 自己也能藏边栏图标（写 `item.hidden`，持久化在 workspace.json），而且它在 `loadLayout` 里盖在我们后面，所以那把锁永远更硬。设置页的说明文字如实交代了这件事并指了路；公开 API 读不到 `item.hidden`（`WorkspaceRibbon` 在 obsidian.d.ts 里是个空类），为此再开一处非公开 API 的口子不值得。

代价说清楚：本次会话内新勾上的图标会追加在那一列末尾而不是插回它在花名册里的位置，下次重载归位。这个代价换来的是「当场看得见变化」，而顺序本来也不完全归我们——用户可以在 Obsidian 里拖着排。

## 与外部的接线

对上只暴露一个装配入口 `registerRibbon(ctx)`，它返回一个「按当前设置重新决定哪几个图标露面」的同步函数，由 main 转交给设置页——与外观开关用的是同一套填洞手法，依赖图仍是一棵树。

装配顺序是硬约束：它必须排在全部命令注册之后。它是照着花名册摆图标的，花名册上还没有的命令，这里也就摆不出来，而这种漏摆不报错——那条命令只是安静地不出现在设置页的清单里。main.ts 的装配段因此把 `registerRibbon` 放在最后一步。

删掉本模块，二十三条命令一条都不少，命令面板照常可用；损失的只是那列图标，以及命令面板里的图标（`Command.icon` 引用的名字没人注册，Obsidian 遇到认不出的图标名只是不画，既不报错也不影响命令执行）。
