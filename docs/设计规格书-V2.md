## 0. 总则

### 0.1 V2 要长出来的东西

初始化后学员的库里直接站着两套系统：**人脉管理**（谁在变冷、谁欠谁人情、谁该送礼）与**复盘**（日→周→月→季→年一条主题链）。客户与付费是第三套，不进默认初始化，由一条独立命令按需长出。

### 0.2 四条已拍板的路线（不再讨论）

| # | 决定 | 理由 |
|---|---|---|
| 1 | **视图由插件自渲染代码块**，不用 DataviewJS | 笔记里只留一行块名，逻辑全在 `main.js`；升级即全库生效，学员改不坏；DataviewJS 保持上游默认关闭，V1 规格 §3 不破 |
| 2 | **人脉+复盘进初始化，客户由命令按需长出** | 大多数学员不做生意，默认不给六张永远空着的销售表 |
| 3 | **新增 `05-diary`，根目录变七个** | PARA 四象限分的是「东西属于谁」，复盘分的是「什么时候发生」；两种坐标轴不塞进同一格 |
| 4 | **日主题建笔记时不问，由命令回填** | 主题是对一天的结论，早上答不出；实测强制弹自由文本 34/34 收到「123123」类垃圾，而垃圾能通过一切非空校验 |

### 0.3 三条红线在 V2 的具体含义

1. **人主导**：视图只在代码块被渲染时计算，重算由 `metadataCache` 变更事件触发，**不得引入任何 `setInterval` 轮询**（Dataview 的 2500ms 刷新正是我们不采用它的原因之一）。
2. **脚本驱动**：日记模板的**天气块整体删除**——它 `fetch` 三个 Open-Meteo 接口，插件内零网络请求不可破。地点/天气/温度三个字段一并从模板移除，不留空键（空键是登记表，不是索引）。
3. **只用官方公开 API**：视图引擎只允许用 `metadataCache.resolvedLinks`、`metadataCache.getFileCache().listItems/frontmatter`、`metadataCache.getFirstLinkpathDest`、`vault.cachedRead`、`MarkdownPostProcessor` / `MarkdownRenderChild`。**禁止** `getBacklinksForFile` 等未在 `obsidian.d.ts` 导出的内部方法。

### 0.4 V2 顺手关掉的两个缺口

- **`archived` 字段缺失（必修）**：`transitions.ts` 当前只写 `status`（`transitions.ts:287`），归档时刻无处可查。归档又走 `guard.mark`，`updatedMaintainer` 被自写抑制，连 `updated` 都不刷——「本月完成的项目」会把完成日记到学员最后一次手打该笔记的月份。修法见 §5.4。
- **`90-system/系统配置.md` 不再需要**：它存在的唯一理由是库内 dataviewjs 读不到插件设置。视图搬进插件后直接读 `ctx.settings.archiveFolder`，位置依赖彻底收敛到设置页，该文件不生成、不提及。

## 2. 视图引擎（V2 的核心新架构）

### 2.1 分层与归属判据

沿用 `core/CLAUDE.md` 的既有判据——**谈业务概念的归 modules，只谈文件事实的留 core**：

```
core/vaultIndex.ts   反向链接索引、列表行读取、字段读取        ← 不认识「人脉」
core/table.ts        表格 / 空态 / 提示的 DOM 渲染             ← 不认识「人脉」
core/codeblock.ts    ziminos 代码块解析、分发、生命周期与重算  ← 不认识「人脉」
core/markdown.ts     往指定小节里插一行（落地新增）            ← 不认识「人脉」
core/time.ts         日粒度口径与五级周期算术（扩充）          ← 不认识「人脉」
modules/*/…Views.ts  口径与语义（谁算超期、账本行怎么分段）    ← 业务全在这里
```

**落地差异一 · 新增 `core/markdown.ts`。** 三条命令都要往既有笔记的某个小节里追加一行（记人情写进日记、增加付费写进客户档案、记收款写进项目 MOC），规则完全一样。规则只该存在一份，而它不谈任何业务概念，所以归 core。

### 2.2 `core/vaultIndex.ts`

```ts
export interface ListLine {
    text: string;            // 去掉列表标记后的整行文本
    isTask: boolean;
    checked: boolean;
    links: string[];         // 行内 wikilink 的原始 linktext（未解析）
    line: number;
}
export class VaultIndex {
    backlinksOf(file: TFile): TFile[];
    resolve(linktext: string, sourcePath: string): TFile | null;
    listLinesOf(file: TFile): Promise<ListLine[]>;
    invalidate(): void;
}
export function dayOfFile(file: TFile): string | null;   // 文件名恰为 YYYY-MM-DD 才有值
```

四条必须写进实现的约束：

1. **反向索引一次构建，全渲染周期共享**。`resolvedLinks` 是 `Record<源, Record<目标, 次数>>`，逐个档案去正查是 O(人数 × 全库)。改为**一次遍历建 `Map<目标路径, TFile[]>`**，缓存到下一次 `metadataCache` 变更为止。这是 V2 唯一的常驻缓存，且由事件失效，不是轮询。
2. **行级链接必须经 `resolve()` 比对路径，禁止字符串匹配**。`listItems` 只给位置不给文本，链接更是原始 linktext；`[[张三|老张]]`、`[[人脉/张三]]`、`[[张三#约定]]` 三种写法指向同一文件。移植源 `person-ledger.js` 用正则拼文件名规避此事，V2 用 `getFirstLinkpathDest` 做得更正确——**这是允许优于原脚本的一处**。
3. **`listLinesOf` 靠 `cachedRead` 取文本，按 `listItems[].position` 切行，结果按 `file.stat.mtime` 缓存**。调用方永远只对「反链指向我的那几篇日记」调用它，不扫全库。
4. **`dayOfFile` 只认文件名，不认文件夹**。全库唯一的日记判据，与演示库口径一致（学员挪走 `05-diary` 也不坏）。

### 2.3 `core/codeblock.ts` 与块语法

学员在笔记里写的是：

````markdown
```ziminos
人脉名录
```

```ziminos
主题链
范围: 周
```
````

- **单一语言标记 `ziminos`**，第一非空行是视图名（中文，学员读得懂），其后每行一个 `键: 值` 参数，半角/全角冒号都接受。
- 未知视图名 → 渲染一行友好提示 + 当前可用视图清单，**不抛异常、不留白块**。
- 每个块包成 `MarkdownRenderChild` 并交给 `ctx.addChild()` 托管；`onload` 内订阅 `metadataCache.on('changed')`，带 200ms 防抖后重算；`onunload` 由基类自动解绑。
- 视图渲染函数签名：

```ts
export interface ViewContext {
    el: HTMLElement;
    sourcePath: string;                    // 宿主笔记路径：视图靠它知道「我长在谁身上」
    params: Record<string, string>;
    index: VaultIndex;
    ctx: ZiminosContext;
}
export type ViewRenderer = (view: ViewContext) => Promise<void>;
export interface ViewDefinition { readonly name: string; readonly render: ViewRenderer; }
export function registerViewCodeBlock(ctx: ZiminosContext, views: readonly ViewDefinition[]): void;
```

`main.ts` 只多一行装配：把三个模块导出的视图数组拼起来注册。**客户视图始终注册**（只读渲染，零成本），开关只决定初始化产物——避免任何需要重启才生效的条件分支。

### 2.5 渲染层纪律

- 表格一律经 `core/table.ts` 的 `renderTable(el, headers, rows)` 产出，单元格支持 `string | TFile | HTMLElement`；**禁止两次 `renderTable` 拼一张逻辑表**（两个 `<table>` 各自算列宽会错位，`review-daily-output.js` 的注释里已记录此教训）。
- 空态一律显式：`📭 + 一句话告诉学员下一步做什么`，禁止空块。缺记录的格子写「（无日记）」，**禁止兜底成 0**——16% 覆盖率下把空值伪装成零值，是最容易骗人的画面。
- 年度全景的柱状图沿用原脚本的纯 DOM + inline style 实现，不引入图表库，不新增 `styles.css`。

## 3. 人脉模块（`src/modules/contacts/`）

### 3.1 数据模型（逐条继承演示库，不发明新键）

人物档案 frontmatter，顺序即呈现顺序：

```yaml
aliases: · description: · created: · updated: · tags: · UID:
type: person
up: "[[人脉MOC]]"     # 归属链接，名录按它分组
tier:                 # 密/近/熟/远 = 7/30/90/365 天联系节奏
direction:            # 向上/平行/向下
gift:                 # true 即进投喂名单
address:              # 整串寄件信息，不参与筛选，唯一雇主是投喂名单
get:                  # 他能给我什么（List）
birthday:
```

三条不可动摇的口径：

1. **卡片不带分类**。没有「客户/生活/工作」枚举；圈子靠 `up`，客户身份靠「名下有 `client` 指向他的项目」从事实反推。身份因此不互斥。
2. **`client` 与 `with` 不能互换**。`client` 是商业契约标记，写下它等于把人注册成客户；朋友一起做的事走 `with`。
3. **位置无关**。全部视图靠 `type` 认身份，唯一位置依赖是 `settings.archiveFolder`（归档即退出名录）。

### 3.2 记录分工（三类记录同一入口，靠行的形态分流）

学员只在**当天日记**里写字，档案自己检索：

| 写法 | 落到哪 |
|---|---|
| `和 [[张三]] 去了新疆，谈定一起投网咖` | 档案「关键事件」 |
| `- [ ] 出网咖投资方案给 [[张三]]` | 档案「待办」 |
| `- [[张三]]｜去｜送了半斤生普｜两清` | 档案「人情账本」+ MOC「人情余额」 |

账本行纪律：全角 `｜` 分隔，`去/来` 必居第二段，状态取 `两清/我欠/他欠`（省略即两清），**人物归属只认首段的链接**——事项里被提到的人不算债主。非法状态值以 `⚠️` 前缀暴露，不静默吞掉。

### 3.3 文件清单

| 文件 | 职责 |
|---|---|
| `templates.ts` | 人脉/客户档案与两张 MOC 的文本生成，纯函数无副作用 |
| `createContact.ts` | 命令「新建人脉」：姓名 → 分层 → 方向三连问，`type: person` 由命令填、模板留空（模板自带 type 会让它自己变成名录里的一个人） |
| `recordFavor.ts` | 命令「记人情」：选人 → 去/来 → 事项 → 状态，账本行追加进当天日记；事项内全角 `｜` 清洗为半角防段错位；日记目录缺失自动创建，不以报错阻断 |
| `personViews.ts` | 档案四视图 |
| `circleViews.ts` | 人脉MOC 四视图 |
| `identity.ts` | 「谁还算数」的唯一答案处（落地新增）：身份靠 type、退出靠归档目录、最近联系只认日记 |
| `ledger.ts` | 日记三类记录的解析层（落地新增）：形态分流与「债主只认首段」的判据 |
| `client.ts` | 命令「初始化客户模块」「新建客户」「增加付费」「记收款」，以及 clientSeed |

| `seed.ts` | 人脉模块的开荒贡献 |

**落地差异二 · 拆出 `identity.ts` 与 `ledger.ts`。** 两处判据被命令侧与视图侧共同消费：「谁还算数」与「一行账本怎么归属到人」。留在任一视图文件里，另一侧就得抄一遍，而抄错的表现是视图静默少一行。

选人列表走 `metadataCache` 筛 `type: person`（客户命令筛 `type: client`），**归档目录内的人不进候选**。人机问答一律用 `core/modals.ts`，多选场景需要新增 `SuggesterModal`（基于官方 `FuzzySuggestModal`）——**枚举取代自由文本，让垃圾在语法上不可能产生**。

### 3.4 与 V1 既有自动行为的咬合（必须验证）

- `cardInit` 的放行闸是 `hasValue(frontmatter.type)`，`type: person` 的档案因此不会被补上 `rating/author/source/up` 四个无雇主的键——V1 已修对，V2 依赖它，回归测试必须覆盖。
- `02-areas/人脉/` 落在 `areaFolder` 内：插件建档走 `guard.mark` 不触发自动登记；**学员手工新建空笔记仍会被当卡片初始化**，这是既有行为，README 里说明「建档用命令」。

### 3.5 付费记录（客户模块）

任务行 + 中文行内字段，一笔一行不嵌套：

```markdown
- [x] [产品::Obsidian课] [金额::365] [日期::2025-08-19]
```

未勾＝待交付，勾上＝已交付，checkbox 直接充当交付状态。三条格式纪律各躲一个已核实的坑：键名用中文（含大写的键会被补一份规范名致求和双计数）、一笔一行（父子字段各自扁平上浮会丢配对）、产品名写在值里（当键名则算总收入必须枚举所有产品）。不设「付费次数/累计金额」字段——数行数即次数，求和即累计。

**V2 自渲染的红利**：这三条纪律里前两条是 Dataview 的解析行为所致；插件自己解析行内字段时不重蹈覆辙，但**格式仍按原样交付**，因为学员的库里可能同时装着 Dataview，两边看到的必须是同一笔账。

## 4. 复盘模块（`src/modules/review/`）

### 4.1 主题链

五级复盘的骨架不是数据，是一条主线：**日主题 → 周主题 → 月主题 → 季主题 → 年主题**。学员只在日记里写一次结论，其余四级全是它的投影。左边一句话是人写的，右边全部自动，两者并排才构成一次复盘。

### 4.2 周期笔记契约

| 级别 | `type` | 文件名 | 目录 | 周期锚点 |
|---|---|---|---|---|
| 日 | `diary` | `YYYY-MM-DD` | `05-diary/01-daily` | 文件名即日期，**无 `period_start`** |
| 周 | `weekly` | `GGGG-Www` | `05-diary/02-weekly` | `period_start` = ISO 周一 |
| 月 | `monthly` | `YYYY-MM` | `05-diary/03-monthly` | 月首日 |
| 季 | `quarterly` | `YYYY-Qq` | `05-diary/04-quarterly` | 季首日 |
| 年 | `yearly` | `YYYY` | `05-diary/05-yearly` | 年首日 |

**统一汇总键 `period_start`**（`YYYY-MM-DD` 定宽字符串）。所有区间比较一律降到 `YYYY-MM-DD` 字符串空间——定宽格式字典序即时间序，零日期算术、零跨年 bug、零跨类型比较陷阱。周归属月用 ISO 惯例：`period_start + 3 天`（周四）落在哪个月，该周就算哪个月，每周只归一个月，不重不漏。

导航行 `<< [[前]] | [[后]] >>　↑ [[上级|本周]]`：上级笔记不存在时是未解析链接，点击即按模板创建，这是 Obsidian 原生行为，不做额外处理。

## 9. 真机第一轮暴露的两处修正（v0.4.0 内修订）

### 9.1 选择弹窗永远返回「取消」

`ChoiceModal` 基于 `FuzzySuggestModal`。Obsidian 的 `SuggestModal` 在用户选中一项时是**先 `close()`、再回调 `onChooseItem`**，而 `onClose` 里同步把 Promise 结算成 `null`，于是每一次正常选择都先被判成取消，随后的 `onChooseItem` 因 `settle` 幂等而失效。表现：新建人脉 / 新建客户 / 记人情 / 增加付费四条命令永远只说「已取消」。

修法：`onClose` 先调 `super.onClose()`（基类自身的清理不能被覆盖掉），再把 null 结算推迟一拍。选中路径由 `onChooseItem` 先落定，取消路径没有后续回调、一拍后照常结算成 null。两条路径都成立，且不依赖基类的实现顺序。

### 9.2 UID 从 17 位字符串改为 14 位数字

属性面板要求 `UID` 是数字类型，而 JavaScript 安全整数上限是 `9007199254740991`（16 位）。17 位的 `YYYYMMDDHHmmssSSS` 一旦以数值形态落盘就会被静默四舍五入——真机第一轮已观测到 `UID: 20260812165253780` 这样末位归零的值，不报错、值已变，且此后每次读写都在错误值上继续。同一个库里还同时存在带引号的 `UID: "202608121704..."`（模板直接写字符串）与不带引号的形态，属性面板一半显示文本一半显示数字。

修法：`UID_FORMAT` 改为 14 位 `YYYYMMDDHHmmss`（2.03e13，稳在安全线内），`nowUid` / `nowStampAndUid` 返回 `number`，全部生成器落盘不加引号。代价是同一秒内建的两篇笔记会撞号——命令都是人触发的，一秒一篇是现实上限，这个代价远小于「主键会悄悄改数」。14 位也正是课程属性注册表 v4 原本写的位数。

### 9.3 属性类型不再需要学员手动设置

Obsidian 决定属性控件的依据是 `.obsidian/types.json`，它不看笔记内容——模板里的空字段因此一律显示成「文本」。

修法两件：其一，`vault/.obsidian/types.json` 随库交付，登记全部 25 个属性的类型（文本 12 / 日期时间 2 / 日期 3 / 数字 2 / 列表 3 / 勾选框 1 / 内置 2），全新安装即生效，升级只补缺失键不改用户调过的类型；其二，开荒生成 `90-system/属性类型示例.md`，每个属性都带一个格式正确的样例值，按类型分块说明。它住在 90-system 且 `type` 取封闭枚举之外的 `示例`，因此不会混进任何一个视图。

连带把 `up` 的落盘写法改成 YAML 列表（它登记为列表类型），`cardInit` 首次登记也写成单元素列表。

## 10. 真机第二轮暴露的修正（v0.4.0 内修订）

第二轮把插件自渲染的视图与原版 Dataview 并排比对，暴露的全是「像不像一个能用的系统」层面的问题——不是数据错，是呈现错。

### 10.1 建项目漏了归属这一步

移植源 `create-project-moc.js` 是四步：名称 → 归属（自己的 / 客户委托的）→ 选人 → 概述。V1 移植时只留了名称与概述两步，**归属分支整个丢了**——而 §3.1 明明写着「`client` 与 `with` 不能互换」，那条纪律因此没有任何入口去执行，全靠用户手写 frontmatter。

补法：命令恢复四步。顺序照原脚本——概述放最后，前面全是点选，中途取消不至于让人白写一段话；归属必须在动土之前问完，客户委托却没选到人时中止，不留半个空文件夹。选项文案直接把后果写出来，因为这一问是整条流程里信息量最大的一步。（归属那两个选项在 v0.8.1 被拆成三个，理由见 §15。）

候选人住在 contacts 模块，projects 不 import 它——`createProject` 声明一个 `PersonPicker` 的洞，由 `main.ts` 用 `contacts/identity.ts` 的 `pickPerson` 填上。这是 §5.6 那套注入的第三处应用，方向与前两处相反（projects ← contacts）。

### 10.2 渲染层与 Dataview 的三处差距

| 差距 | 后果 | 修法 |
|---|---|---|
| 文本里的 `[[双链]]` 渲染成死文本 | 视图检索出来的是日记原文，原文里的人名与项目名都是双链——拍平成字符串等于把一张关系网变成一段文字，点不动、跳不了 | `core/table.ts` 新增 `RichText` 单元格与 `renderTextWithLinks`，链接按**来源笔记**的路径解析（事件行来自日记，不能按档案路径解析） |
| 任务行渲染成表格 | 待办不像待办，也勾不掉 | 新增 `renderTaskList`：一条一行、真复选框、日期缀在句尾且可点、勾选写回源文件那一行；写前比对原文，行号漂了就什么都不做 |
| 全框线表格 | 与 Dataview 的三线表风格分裂，同一个库里两种表 | 新增 `vault/.obsidian/plugins/ziminos/styles.css`：三线表、首列表头带行数计数、选择器全带 `ziminos-` 前缀、颜色取 Obsidian 语义变量 |

`styles.css` 是插件的第三个交付文件（前两个是 `main.js` 与 `manifest.json`），手工维护、不经 esbuild，已加入 SKILL 的交付清单与升级复制清单。

**只认双链一种标记，不接完整 Markdown 渲染器**：这些文本是用户日记里的原话，交给渲染器等于把用户数据当代码执行，一个 `![[大图]]` 就会在名录里嵌进一张图。

### 10.3 相关项目的口径修正

原实现列「项目 / 关系 / 状态」，且不分状态全列。改为：

- 列 **项目 / 关系 / 概述**——状态这一列在只剩进行中的表里恒定重复，概述才是决定要不要点进去的信息。
- **只列未终结的项目**。走到 `done` 或 `dropped` 的项目从「相关项目」移进「关键事件」，带着 `archived` 给的确定日期。理由是这四个视图本就是一条时间线：相关项目答「我们现在手上有什么」，关键事件答「我们之间发生过什么」。一个三年前做完的项目永远挂在「相关项目」里，是把履历当成待办。


### 10.4 版面：表格占满整行，待办收成一行

真机第三轮的反馈是「自适应到了最小宽度」——表格缩成内容宽度挤在左边，右侧大片空白没人用；待办则被日期分组标题拉长了一倍。两件都是空间分配问题。

**表格**：`.ziminos-table` 这一级压不住 Minimal 给 table 设的收缩宽度，选择器改成 `div.ziminos-table-wrap > table.ziminos-table` 两级。光撑满还不够——余量得有人收：`renderTable` 新增可选的 `grow` 参数指出哪一列是句子列，其余列 `width:1px + nowrap` 各取所需，句子列拿走全部余量。只在真有句子列的表上指定（概述、事项、发生了什么、一句话、寄件信息、各级主题、笔记），其余交给浏览器均摊。

**待办**：去掉按日期分组，改走与其余视图同一个 `renderTable`，画成三线表（事项一列、日期一列，事项列吃余量）。复选框与事项同处一格——分成两列的话一个待办会被表格的列切成两半，而勾选框离它要勾的那句话越远越容易勾错。格内用 flex 两段，事项段显式 `min-width: 0`：flex 子项默认 `min-width: auto`，长句子会撑破单元格。

**全宽**：两级选择器仍不足以撑满——主题可能用 `!important` 锁死表宽，那场特异性竞争赢不了。改用 `min-width: 100%`：它不参与竞争，浏览器先算出 `width` 的用值再拿 `min-width` 去夹，于是无论主题把 `width` 设成 `fit-content` 还是别的什么，最终宽度都不会小于整行。这比自己也写一个 `!important` 干净——我们并没有覆盖主题的意图，只是声明一条下限。


## 11. 左侧边栏命令与图标（v0.5.0）

### 11.1 要解决的问题

命令面板对零基础学员是隐形的。他知道「记灵感」这件事，却未必记得住 `Ctrl+P` 再打三个字；而一条命令只要点不到，它在产品里就等于不存在。社区插件 Commander 解决的正是这个问题——把命令摆到最左边那一列图标里。

不装 Commander 而自己长出来，理由不是少一个依赖，是**图标要与命令同源**：命令改了名、换了图标，边栏上那个按钮必须当场跟着变。插件之间做不到这件事，只能各存一份，而各存一份迟早对不齐——对不齐既不报错也没人发现。

### 11.2 命令注册台（`core/commands.ts`）

二十三条命令的身份（`id` / 中文名 / 图标名 / 分组）从 `constants.ts` 里分出来，连同注册台一起住进新文件。分家的判据是：`constants.ts` 回答「系统里有哪些东西」，`commands.ts` 回答「用户能让系统做哪些事」；命令还多带了图标与分组两样只服务界面的字段，混进常量表会让那份表同时是数据字典和界面清单。分家后 `constants.ts` 从 575 行回到 531 行，没有触碰单文件 800 行的红线。

`CommandRegistry` 做两件必须同时做的事：把命令交给 Obsidian（命令面板与快捷键因此找得到它），同时在花名册上留一份（左侧边栏因此有东西可摆、设置页因此有清单可列）。全部模块改走 `ctx.commands.register(spec, run)`，`plugin.addCommand` 在业务代码里不再出现。

**花名册存回调本体而不只是 id**，这是本次唯一一处需要解释的取舍：按 id 执行命令的 `executeCommandById` 不在 `obsidian.d.ts` 里。为了让边栏按钮能触发命令而再开一个非公开 API 的口子，代价远大于收益——而回调本来就在手上，接住即可。**因此本次新增功能全程只用公开 API（`addIcon` / `addRibbonIcon` / `Command.icon`），不构成第 4 处红线偏离。**

两处顺带的收敛：`TRANSITION_COMMANDS` 从 `transitions.ts` 搬进来（它本就该与 `TRANSITIONS` 状态机同处一地）；`PERIODS` 里的 `commandId` / `commandName` 搬成 `PERIOD_COMMANDS`，键是 `PeriodKey` 且类型是 `Record`，于是「加一级周期却忘了给它命令」在编译期就过不去，而 `PERIODS` 那张表回归只谈时间。

### 11.3 二十一个图标（`modules/ribbon/icons.ts`）

出自同一套画法（Pikaicons：24 格、2 宽描边、圆头圆角）。十六个取自免费集原图，五个照同一套画法补画——暂停、播放、灯泡、调色板在免费集里没有，四分之一饼则必须与兄弟图标成套才讲得清「季」。补画的一律复用原图的几何原语（半径 9 的圆、日历框），因此它们与原图并排时看不出接缝。许可与来源见 `docs/第三方组件.md`。

| 分组 | 命令 | 图标 | 为什么是它 |
| --- | --- | --- | --- |
| 开荒 | 初始化笔记库 | 三层叠片 | 开荒做的就是一次把层次铺好 |
| 项目 | 新建项目 | 旗 | 项目与领域的区别是它有终点，而旗子插在终点上 |
| 项目 | 初始化当前卡片 | 一页纸 | 它做的就是把眼前这一页登记成卡片 |
| 项目 | 完成 / 暂停 / 放弃 / 重新开始 | 圈中勾 / 双竖 / 叉 / 播放 | 四个共用同一个半径 9 的圆，只换圆心里的记号——它们是同一台状态机的四个出口 |
| 灵感 | 记录灵感 | 灯泡 | 免费集里没有，补画；两道螺纹不能省，只留一道会读成气球 |
| 复盘 | 日 / 周 / 月 | 日历框 + 点 / 横条 / 网格 | 同一个框，一天是一个点、一周是一行、一月是一片 |
| 复盘 | 季 | 四分之一饼 | 再密的格子在 18px 下都和月记一样；「四分之一」只有饼图不会被误读 |
| 复盘 | 年 | 勋章 | 年度复盘是一年的结算，不是更大的一格日历 |
| 复盘 | 写复盘主题 | 笔 | 五级里唯一要动笔写的字段 |
| 人脉 | 新建人脉 | 人 + 心 | 人脉与客户的分别就在这颗心上 |

| 客户 | 增加付费 / 记收款 | 钱 / 钱包 | 付费是承诺，收款是钱真的进了口袋，两件事两个图 |
| 外观 | 打开外观开关 | 调色盘 | 免费集里没有，补画 |

两处技术决定：

1. `addIcon` 把内容塞进一个 `0 0 100 100` 的外层 svg，我们再套一层自带 `0 0 24 24` 的内层 svg 把 24 格铺满，而**不是**把每个坐标乘以 4.1667——`path` 里的数字是设计稿上的数字，换算过一遍就再也改不动了。
2. 描边宽度取 `var(--icon-stroke, 2)` 而非写死 2。ziminOS 随库交付 Minimal + Style Settings，学员在外观面板里把图标调细时，只有这二十三个不跟着变的话，那一列会一眼看出是外来户。

### 11.4 摆法（`modules/ribbon/dock.ts`）

默认摆出七条：新建项目、记录灵感、今天的日记、写复盘主题、新建人脉、记人情、外观开关。判据是「一天里可能按不止一次」。其余十六条要么一辈子只按一次（初始化笔记库、初始化客户模块），要么发生在某个具体场景里（初始化当前卡片、四条流转、三条客户流水、周月季年四级复盘）——那些场景里用户本来就停在对的笔记上，命令面板比一根图标柱更快。二加十二，正好十四。二十三条全摆等于把选择的负担丢回给学员。

**只为勾上的命令调 `addRibbonIcon`**，不是一次建齐二十一个再切显隐。第一版正是后者，被真机核对推翻，两次判断都记在这里：

`WorkspaceRibbon.onChange()` 遍历它自己那份 `items`，对每一项无条件执行 `buttonEl.toggle(!item.hidden)`——**inline 的 display 是 Obsidian 保留给自己的通道**，而 `item.hidden` 只有它的边栏菜单能改，公开 API 里没有入口。于是第二次启动（`workspace.json` 里一旦存下 `left-ribbon`，`loadLayout` 就会调 `leftRibbon.load` → `onChange`）、装任何一个也调 `addRibbonIcon` 的插件、用户在边栏右键或拖一下，都会把二十一个图标全放出来，而设置页还显示「已摆出 7 条」。

更根本的一层是 DOM 修不好的：手机端底栏的边栏菜单与桌面「设置 → 外观 → 功能区 → 管理」弹窗都遍历 `leftRibbon.items`、只看 `item.hidden`，不看 DOM。一次建齐的话，那两处永远列着全部二十三条——包括「初始化笔记库」。只建勾上的，这两处才跟着对。

本次会话内取消勾选的按钮收不回来（没有公开的「撤下这一个」），只能加一个 `.ziminos-ribbon-hidden` 先藏起来，下次重载它压根不会被建出来。在那之前它仍留在 `leftRibbon.items` 里，于是另外三处入口照旧列着它、点了还照旧执行：手机端底栏的边栏菜单、桌面「设置 → 外观 → 功能区」的管理弹窗、边栏空白处的右键菜单。桌面上无伤——边栏那一列是主入口，用户看到的就是消失了；**手机上则完全看不出变化**，因为 `.is-phone .side-dock-ribbon` 本来就是 `display:none`，手机根本没有那一列。为此 `syncVisibility` 在手机端取消勾选时弹一句「重启后才会从边栏菜单里消失」，把疑惑变成预期。这条 CSS 是 `styles.css` 里唯一的 `!important`：它压的不是主题的设计意图，而是「用户取消了勾选，这个图标就必须消失」这条没有商量余地的声明，输掉那场特异性竞争等于功能不存在。代价是本次会话内新勾上的图标追加在末尾而非插回原位，重载归位——而顺序本来也不完全归我们，用户可以在 Obsidian 里拖着排。

**另一处如实备案：两把锁，且另一把不归我们**。Obsidian 自己也能藏边栏图标（边栏右键，或「功能区」管理弹窗里的删除），它写的是 `item.hidden` 并持久化进 `workspace.json`。启动顺序是插件先建按钮、`loadLayout` 后把 `hidden` 盖回来，所以那把锁永远压过我们这把：一条命令可以在 ziminOS 设置页显示为已勾选、边栏上却始终不出现，而且在 ziminOS 里反复拨开关也救不回来——只能回 Obsidian 的「其他功能区项目」里放出来。公开 API 读不到 `item.hidden`（`obsidian.d.ts` 里的 `WorkspaceRibbon` 是个空类），要读只能再开一处非公开 API 的口子，不值得。当前处置：设置页的说明文字如实交代这件事并指路，代码不做检测。

**一处如实备案，没有在本次修掉**：二十三条里只有「初始化当前卡片」可能被点了完全没有反应。它的守卫是静默放行（不在项目/领域目录二级以下、已登记过、是 MOC 本体、没有活动文件，一律直接返回不作声），那是 `initialize-card-note.js` 的移植纪律——原脚本的守卫与文案一字不改，要给它补提示得先在规格里授权。在真实使用的库里这不是边缘情况：日记、五级复盘、灵感集、人脉、客户、模板、导航页，以及所有已登记过的卡片，点下去都是零反馈。从命令面板执行同样如此，所以它不是本次引入的缺陷，但把它做成一个亮闪闪的图标确实放大了它。当前处置：**不进默认清单**（学员要主动勾才会遇到），行为一字不改。要不要给它补一句「这篇笔记不在项目或领域目录里，不需要登记」，是一个需要单独拍板的产品决定，因为它会动到一条写在 modules/projects 的 L2 里的移植不变式。

**第三个入口带来的一个连带修正**：外观开关的浮层原本只放行状态栏按钮，边栏那个调色盘按钮不在名单里，于是点它一下会被同一次手势处理两遍（mousedown 判定「点了别处」先关，click 再开回来，浮层闪一下还在）。改法不是扩充放行名单——「谁能打开我」会随入口增加而增长，名单迟早漏掉一个——而是记下「上一次因点别处而关闭」的时刻，同一次手势内的再次打开直接忽略。判据与 `SelfWriteGuard` 同形：都是在问「这动作是不是我自己刚才引起的」。

### 11.5 设置页第五区

`ribbonCommands: readonly string[]` 存已勾选的 id。声明成 `readonly` 不是洁癖：它在用户没调过时与 `DEFAULT_SETTINGS` 共用同一个引用，允许原地 `push` 的话，用户第一次勾选就把默认值本身改掉了，此后连「恢复默认」都恢复不回来——这条约束交给编译器执行，不靠人记得。每次勾选都照花名册重排一遍生成新数组，顺带把 `data.json` 里不认识的 id 扫掉。

设置页那一区不认识任何一条具体命令，清单现读花名册，分组标题按相邻两行的 `group` 变化切出来（与外观开关面板同一套画法）。每行左侧画出该命令的真实图标——勾之前先让人看见它长什么样。

设置页要让边栏那列已经画出来的图标跟着变，于是多了第四个「函数类型的洞」。三件注入的事（执行开荒、同步状态栏、同步边栏）改由 `SettingActions` 一个对象递进来，而不是三个位置参数：后两个的类型都是 `() => void`，摆成位置参数时调换顺序照样能通过编译，出的错却没有任何编译期信号。

### 11.6 交付物同步

`vault/README.md` 是学员手册，它通篇教「按 `Cmd + P` 输入命令名」——而那正是本功能要消灭的摩擦，不改它等于功能做了没人知道。三处改动：

- 开荒三步之后新增「先看一眼最左边那一列」，用一张「图标长什么样 → 它做什么」的对照表交代默认七条，并说明另外十四条在设置里勾。
- 明说下文每个动作仍写 `Cmd + P` 那条路，因为二十三条都能那么走，而边栏上只有勾过的那几个——两条路通向同一件事。
- 小提醒里补一条「关于左边那列图标」，如实写明两件反直觉的事：取消勾选后手机端边栏菜单要重启才彻底干净；在 Obsidian 自己的「功能区」里藏掉的，回 ziminOS 勾上也不会出现。

`skill/SKILL.md`（桌面 Agent 的安装契约）里的交付话术也该加一句「最左边多了七个图标」，那份文件不属于本节范围，由发布流程一并处理。

### 11.7 验收

1. 全新库首次加载，左侧边栏出现七个图标，顺序为：新建项目、记录灵感、今天的日记、写复盘主题、新建人脉、记人情、外观开关。

4. 取消全部勾选，边栏上 ziminOS 的图标一个不剩，命令面板里二十三条一条不少。
5. 命令面板搜「ziminOS」，每条命令左侧带着与边栏相同的图标。
6. 在 Style Settings 里调粗/调细图标描边，这二十一个跟着变。
7. 切换明暗主题，图标颜色跟随（取 `currentColor`）。
8. 老库升级（`data.json` 里没有 `ribbonCommands`）：默认七条正常出现，其他设置一项不丢。

10b. 手机端取消一条勾选：应当立刻看到一句「重启后才会从边栏菜单里消失」的提示（手机上没有边栏图标柱，没有这句话就完全没有反馈）。
11. 边栏上点调色盘图标：浮层开；再点一次，浮层关（不是闪一下又开回来）。
12. 手改 `data.json` 把 `ribbonCommands` 写成 `null` 或字符串，重开：设置页七个分区完整可见，边栏回落默认七条。

## 12. 设置页按系统模块分页（v0.6.0）

### 12.1 起因

真机截图给出的判据很直白：一页排下来是开荒、两个自动化开关、五项灵感、一个外观开关、二十一行边栏、九个折叠的目录字段、七行模块清单——**四十来个控件排成一条长路**。想改灵感的落点得越过边栏那二十一行，想改产品清单得先想起它藏在一个叫「高级设置（一般不用改）」的折叠区里。这不是控件多，是**没有边界**：一页同时回答了七个系统的配置问题，于是每个问题都得从头找起。

而边界本来就存在，只是没有在界面上显现——`src/modules/` 下那七个目录就是它。设置页不做分页时，代码的模块边界与用户看到的顺序是两套东西，「客户的设置在哪」的答案取决于当初谁把它排在了哪一段。

### 12.2 切法：一页一个模块，页标识与目录同名

八张页：`setup` / `projects` / `inspiration` / `review` / `contacts` / `clients` / `appearance` / `ribbon`。前七个同名于 `modules/` 下的目录，`clients` 是 `contacts` 模块里 `client.ts` 那一支——单列成页的理由与它在 `COMMAND_GROUPS` 里单列成组的理由是同一条：客户与人脉在业务上本就是两个物种。

标签一律两个字（开荒 / 项目 / 灵感 / 复盘 / 人脉 / 客户 / 外观 / 边栏）。长短不齐的标签会让人以为它们不是一类东西；八枚两字标签加图标约 610px，在设置弹窗内容区里一行排得下，窄窗口自动折行。

顺序即学员的使用顺序，也正好是 `main.ts` 的装配顺序与命令的注册顺序：先开荒，再是每天在用的三套（项目、灵感、复盘），然后是关系与生意（人脉、客户），最后两张管的都不是笔记而是屏幕（外观、边栏）。

### 12.3 目录字段各回各家

原来九个目录/格式字段全堆在页尾一个统称「高级」的折叠区里。分页之后它们各自归还给服务的那个模块：项目/领域/归档三个目录归项目页，复盘目录归复盘页，人脉目录归人脉页，客户目录归客户页，时间格式归开荒页（它服务全库的 created/updated，没有别的模块能认领它）。

**`clientSources` 与 `clientProducts` 就此离开折叠区**。判据不是「难不难懂」，是「改了会不会让学员的库与课程讲义对不上」：目录名与时间格式是课程内容的一部分，所以既要留出口又不能摆在明面上诱导人去动；而渠道与产品清单本来就是学员自己的业务数据——产品名只能由他自己写，把它锁进一个叫「一般不用改」的抽屉里才是真的误导。

每页仍有自己的「高级设置（一般不用改）」折叠区，永远在页尾；本页没有高级字段就整块不出现——一个点开来是空的折叠区，比没有它更让人怀疑自己漏了什么。

### 12.4 一张表喂三处

`TABS` 是八张页的唯一身份表（短名 / emoji / 模块全名 / 交付状态），同时喂：标签栏、每页页头那句「这一页是谁、跑没跑起来」、开荒页那份「系统模块」清单。于是不可能出现「标签上写着外观、清单里写着外观包 v2、页头又是第三句」。

**第一版还在开荒页上列了一份逐行可点的模块清单，随即摘掉**：九张标签一直摆在屏幕最上方、点一下即到，在首页把同样九行重列一遍，是把「索引」误当成了「介绍」——用户要的是切过去，不是先读一遍目录。那句交付状态没有跟着消失，它就在各页页头，在那儿它回答的是「我现在在哪、这页管什么」，而不是「这套系统都有些什么」。`TABS` 因此只喂两处：标签栏与页头。

十二个文本字段同理收进 `TEXT_FIELDS` 一张表，每条自带 `tab`（这是谁的设置）与 `advanced`（该不该收进折叠区）。一页的骨架固定为**页头 → 明面字段 → 自有控件 → 高级折叠**，这条顺序让灵感页的落点三问天然排在插入位置与格式之前，那一页因此不必自己再画一次字段。

### 12.5 三处实现取舍

- **加一页是编译期的事**。每页自有控件挂在 `Record<TabId, PanelRenderer>` 上，漏写一页是编译错，而不是运行时一张点进去空空如也的页。复盘、人脉、客户三页确实只有目录字段，写成显式的空实现而非让它们缺席，穷尽检查才继续成立。
- **「当前停在哪一页」不进 `data.json`**。设置对象里存的都是「这个库是什么样」，不是「上次那个人翻到了第几页」。它随插件实例存活：关掉设置弹窗再打开仍停在原页，重启 Obsidian 归位——与 Obsidian 自己记住你上次停在哪个插件设置页同一档待遇。
- **标签栏吸顶，换页后滚动条归零**。边栏那页有二十一行，翻到第十八行时标签栏若已滚出视野，换页就得先滚回顶部；而从二十一行的边栏页切到只有一个开关的外观页，滚动条不归零的话用户迎面是一片空白，会以为切坏了。标签是真的 `<button>`（键盘与读屏器认得），只带 `aria-pressed` 不自称 `role=tab`——没实现方向键遍历就自称 tablist 是撒谎。

### 12.6 验收

1. 打开设置 → ziminOS：顶上一排八枚标签一行排开，停在「开荒」页，页头写着「🌱 开荒 v1」。
2. 逐个点过去，每页只出现属于该模块的设置项；八页加起来与分页前的控件一个不多一个不少（十二个文本框、三个开关、一个下拉、一个文本域、一个按钮、二十一行边栏）。
3. 开荒页上只有初始化那一件事，不再重列模块清单；每页页头写着该模块的全名与交付状态。
4. 项目页折叠区里改「项目目录」，去灵感页再回来，值还在（改动即时落盘，与分页前一致）。
5. 客户页的「客户渠道」「产品清单」直接在明面上，不在折叠区里；「客户目录」仍在折叠区里。
6. 灵感页顺序为：文件夹 → 笔记名称 → 定位标题 → 插入位置 → 单条格式，且没有高级折叠区。
7. 边栏页勾选一条命令：边栏立刻变，「已摆出 N / 21 条」立刻变，且页面不跳回顶部。
8. 边栏页滚到底，标签栏仍吸在顶上；点「外观」，落在外观页顶部而不是一片空白。
9. 开荒页点「初始化」：跑完仍停在开荒页，状态说明翻面成「已就绪 ✓」。
10. 切明暗主题与换配色：标签栏、选中态、清单强调条全部跟随（颜色一律取 Obsidian 语义变量）。

## 13. 排版整理（v0.7.0）

### 13.1 起因与现状核对

真机核对先于设计。扫过测试库里那十三篇笔记，两类问题各有一个确凿样本：

- **中英之间没有空格**：`这是一个MOC笔记，现在要写[[卡片笔记]]`（用户手写的项目概述）。
- **空行不合规**：日记里 `## 今天做了什么` 下面两个空行、列表下面又两个空行——那是学员删掉模板留的 `%%` 提示块之后剩下的；以及灵感集的 `# 灵感集` 紧贴着 ```dataview 围栏，那一处是**插件模板自己写错的**，一并修在 `inspiration/templates.ts`。

同时确认了一件更要紧的事：**插件生成的字里，中英相邻只有三处，而且三处都绝对不能加空格**——`人脉MOC.md`、`客户MOC.md` 是文件名兼链接目标，`B站,抖音,小红书` 是渠道候选值（加空格会与已有档案里存的值对不上，渠道统计当场散架）。结论因此是硬的：**这条规则的对象是用户写的字，不是插件的模板**，而它的第一要务是知道哪里不能加。

### 13.2 九条规则住在 core，纯函数且幂等

`core/markdownStyle.ts` 零 import，只认字符串。九条：中英空格、标题/列表/表格/代码块上下留空行、YAML 后留空行、连续空行收一行、去行尾空格、文末一个换行。

**幂等是设计前提而非碰巧成立的性质**：`formatMarkdown(formatMarkdown(x)) === formatMarkdown(x)`。自动整理会写盘，写盘触发 `modify`，`modify` 又排下一次整理——断开这个环靠的正是「第二趟算出来的与第一趟一字不差，于是没有第二次写入」。五十六条断言逐条覆盖，每条都同时验一遍幂等。

八条空行规则合成同一趟扫描，而不是八个独立变换：「标题上下留空行」与「列表上下留空行」在「一个标题紧跟一个列表」这一处是同一个决定，拆开的话它们会各插一行、再靠第九条压掉多余的——那样既慢，也让「为什么这里是一行不是两行」变成一道要追八步才答得出的题。

### 13.3 保护名单：真正的难点

六种东西整段保护：行内代码、`[[双链]]`（连别名）、`[文字](链接)`、裸网址、HTML 标签、`#标签`；YAML 属性区在切分阶段就被摘出去，一个字符都不参与。

**但保护段外面照加**——`打开[[人脉MOC]]看看` → `打开 [[人脉MOC]] 看看`，空格落在方括号之外，链接一字未动。这个区分是整条规则的要害：会断链的是括号里那一个空格，而括号外那一个恰恰是中文与英文之间该有的呼吸。接缝处补不补空格只看一条：一边是汉字、另一边是可见的半角字符；全角标点因此永远不会被塞进空格（`路径，` 与 `。[[链接]]` 都原样）。

标签是个值得记的边界：`#项目2026的事` 在 Obsidian 里是**一整个**标签（标签允许含汉字），从 `2026` 后面切一刀会把它劈成两半。所以整段保护、只在它前面补空格——补完它才真的被 Obsidian 认成标签。

### 13.4 什么时候动手：三个时刻，都不是「你正在打字」

用户选定「命令 + 停手后自动（默认开）」，但**自动整理刻意不碰你正开着的那一篇**。理由是具体的：中文输入法在合成中途被外部改写会吞字；就算不吞字，整篇重写也会把光标从他正打字的位置上移开。「停手两秒」这个信号对 `updated` 那种只改一个 YAML 字段的动作足够，对整篇重排远远不够——斟酌一句话时停两秒太常见了。

于是自动整理只发生在三处：**用户从一篇改过的笔记切走**（`active-leaf-change` 管换面板、`file-open` 管同面板换文件，两个都订，漏一个就会留下永远等不到整理的笔记）；**一篇没开着的笔记被改动**（比如记人情刚往今天的日记里插了一行）；**用户自己按下命令**——那一条不受任何限制。

### 13.5 与 updatedMaintainer 共处一室

两个常驻编辑监听，规矩必须写死：

| | updatedMaintainer | formatter |
| --- | --- | --- |
| 看 SelfWriteGuard 吗 | 看，插件刚写过就跳过 | **不看** |
| 断环靠什么 | 守卫 | formatMarkdown 幂等 + 「没变化就不写」 |
| 改动范围 | YAML 里一个字段 | 整篇 |
| 正在编辑的那一篇 | 照记 | 绝不碰 |

formatter 故意不看守卫，因为插件自己插进去的那一行（记人情、增加付费、记收款、记灵感）恰恰最需要整理——里面有用户现敲的字。它写盘前仍 `guard.mark`，那是给对方看的：整理是机器的动作，不该被记成用户的编辑。代码里另留一把一秒的再入锁，它挡不住设计错误，只是不把「幂等」这条性质押在一句注释上。

### 13.6 设置：一个自动开关 + 九个规则开关

`autoFormat` 回答「谁来按」，`formatRules` 回答「按下去做哪几件事」，刻意不合成一个——自动关掉后命令仍按九条勾选执行，合并就没法表达「我自己按，但按下去要全套」。

`formatRules` 存启用中的规则 id 清单而非九个布尔字段，与 `ribbonCommands` 同法同因：加一条规则不必动设置契约，而老库升级时那条新规则不在清单里、于是默认不开。设置页因此多出第七张标签「排版」（九张页的顺序里它排在客户与外观之间，与命令注册顺序一致），命令总数二十一 → 二十二。

### 13.7 验收

1. 新建一篇笔记，写 `使用Dataview查询3篇笔记`，切到别的笔记再回来：变成 `使用 Dataview 查询 3 篇笔记`。
2. 写 `打开[[人脉MOC]]看看`，同样操作：变成 `打开 [[人脉MOC]] 看看`，**点这个链接仍然能跳到人脉 MOC**（这一条是全功能最关键的回归，断链不报错）。
3. 在一段正文下面紧跟一个列表、一个表格、一个 ```ziminos 代码块，切走再回来：三者上下各空一行，块内一个字未动。
4. 连打五个空行、行尾敲一串空格，切走再回来：空行收成一行、行尾空格没了。
5. 停在一篇笔记里连续打字并中途停顿数次：**它一次都不该动你的字**。此时按 `Cmd + P` →「整理当前笔记格式」，当场整理并弹「已按标准写法整理这一篇 ✓」。

9. 关掉「改完走开自动整理」：切走不再整理，命令照常可用。
10. 「记人情」往今天的日记里插一行（此时日记没打开）：那一行落进去之后自身也被整理过。
11. 手改 `data.json` 把 `formatRules` 写成 `null`，重开：九条回落默认全开，设置页九张标签完整可见。
12. 观察 `updated` 字段：自动整理不应把它推到当前时刻（整理是机器动作，走 `guard.mark`）。

## 14. 新建领域与 MOC 改名（v0.8.0）

### 14.1 MOC 改名：`文件夹名` → `MOC-文件夹名`

**起因**：一个项目是「一个文件夹 + 一篇 MOC」，而此前那篇 MOC 与文件夹同名，于是文件树里父子两级写着同一个词，哪一篇是总览全靠记。加个前缀，它在任何按名字排序的地方都浮到最上面，也一眼认得出。

**改这个名之所以不是改一行**，是因为这个约定有四个消费方：建项目照它落笔、卡片登记照它反推归属、状态流转照它认出「这是不是一篇 MOC」，以及**MOC 正文里那个 base 视图要照它写筛选表达式**。第四处最容易漏——`up == link("项目名")` 收的是 up 指向本 MOC 的卡片，MOC 一改名，这条筛选就再也匹配不上，而**那张表不会报错，只会静默少收一半文件**。四处因此收进 `modules/projects/moc.ts` 一个文件，改一次命名只改一处。

**存量笔记一篇都不改名**。读取侧一律走 `resolveMocPath`：先认 `MOC-名`，认不到再认 `名`，两个都没有时返回新名。三处消费方都吃这条回落，所以 v0.8.0 之前建的项目照样能被卡片认领、照样能执行四条流转。状态流转还多一条纪律：搬的是整个文件夹，MOC 的文件名一个字都不会变，所以目标路径沿用它**此刻**的名字，而不是照当前约定重新拼一个——否则老库的项目会在搬完之后「找不到自己的 MOC」而整体回滚。

### 14.2 新建领域

PARA 里「项目」与「领域」是同一个问题的两个答案：这件事有没有终点。所以它们共用一条流程，差别只有三处，全部收在 `ContainerKind` 那张表里：

| | 项目 | 领域 |
| --- | --- | --- |
| 根目录 | `projectFolder` | `areaFolder` |
| `type` | `project` | `area` |
| 问归属吗 | 问 | **不问** |

不问归属不是省一步，是那个问题在领域上不成立：领域是你对自己某一部分人生的长期关注——健康、手艺、人脉——它天然只属于你自己，问一句「这是谁委托的」是在问一个不存在的答案。

**一处主动的偏离，在此备案**：领域的 frontmatter **不写 `status`**。用户的要求是「只改 type，其余不动」，但导航页那张「正在进行中」正是按 `status == "active"` 筛的——照搬 `status: active` 会让每一个领域都混进那张表，而领域没有终点，说它「正在进行中」本身就是个假命题。少写一行的代价是零：`type == "area"` 那张表照常收得到它，四条状态流转本来就只认 `type: project`。

实现上，`createProject.ts` 里那条流程整体搬进 `createContainer.ts`，项目与领域各留一个薄入口。这样做而不是加两个 if，是为了让「新建领域某天悄悄少一道防覆盖校验」在结构上不可能发生；`label` 取「项目」时它吐出的每一句话与 V2 逐字相同，`create-project-moc.js` 的移植纪律未破。

命令总数二十二 → 二十三，新增图标一枚：一个缺口开在右上的环，与「新建项目」那面旗子成一对反义词——旗子插在终点上，而领域没有终点。它不进默认边栏七条：一个人的领域屈指可数，建完就是好几年。

### 14.3 验收

1. `Cmd + P` →「新建领域」，输入「健康」与一句概述：长出 `02-areas/健康/MOC-健康.md`，全程只问两次，不问「这是谁的」。
2. 打开它看 YAML：`type: area`，**没有 status 行**，没有 client/with。
3. 打开导航页：「领域」那张表里有健康；「正在进行中」那张表里**没有**它。
4. `Cmd + P` →「新建项目」，建「写本书」：长出 `01-projects/写本书/MOC-写本书.md`，问答流程与 v0.7.0 相同（归属三选项见 §15）。
5. 在「写本书」文件夹里新建一篇空笔记，随手写点东西：它被登记成卡片，`up` 指向 `MOC-写本书`，点得动。
6. 打开 `MOC-写本书`，看那个 base 表：第 5 步那篇卡片在表里（这一条验的是 `up == link("MOC-写本书")` 没有写错）。
7. 站在 `MOC-写本书` 上执行「完成项目」：整个文件夹搬进归档，`status: done` 与 `archived` 同时落笔。
8. **老库回归（最关键的一条）**：拿一个 v0.8.0 之前建的项目（MOC 与文件夹同名），在它里面新建卡片 → up 仍正确指向那篇老 MOC；站在老 MOC 上执行「完成项目」→ 照常搬移，不报「只能在以下项目 MOC 中执行」。
9. 站在一篇领域 MOC 上执行「完成项目」：应当被拒绝，提示「当前笔记不是项目 MOC」——领域没有终点这件事在代码里也成立。

## 15. 建项目的归属改成三选项（v0.8.1）

### 15.1 这是一处自相矛盾，不是偏好问题

原流程的归属只有两项：

- 自己的项目（不写 client，不进客户统计）
- 客户委托的（写 client，我欠他一个交付）

选完第一项，紧接着仍会弹一次选人，标题是「和谁一起做？（自己独做就按 Esc 跳过）」。

于是标签刚说完「这是自己的项目」，下一屏就问「还有谁」，而想表达「真的只有我」的唯一办法是**按取消键**。一个必须靠取消才能走完的流程，是在拿取消当确认使——用户按 Esc 的那一刻并不知道自己是取消了选人、还是取消了整个建项目。

### 15.2 改法：把「要不要挂人」并进同一屏

三个选项，一次答完：

| 选项 | 挂什么 | 没选到人怎么办 |
| --- | --- | --- |
| 自己做（只有我，不挂任何人） | — | 不问，直接进下一步 |
| 和别人一起做（写 with，不算客户） | `with` | 照建，只是少挂一条 |
| 客户委托的（写 client，我欠他一个交付） | `client` | **中止**，不留半个空文件夹 |

后两项分家不能省。`with` 不是装饰字段：人脉档案里那张「相关项目」正在读它（`personViews.ts` 按 `client` 或 `with` 指向本人来收项目）。把两项砍成一项、只留 client，等于让「和朋友一起做的事」要么消失、要么被无声注册成一笔商业委托——而后者恰恰是 §3.1 那条「`client` 与 `with` 不能互换」明令禁止的。

必答性也不同，理由在业务里：客户委托却没选到人，那是一笔没有债主的交付债务，不成立；一起做的人没选到，项目照样成立，只是少一条关系。

### 15.3 顺带拆掉一个没人拨的旋钮

`PersonPicker` 此前带第二个参数 `quietWhenEmpty`：库里一个人都没有时要不要吭声。它只为「自己独做但顺口问一句同行者」那条路存在——关联本来可选，所以不该拿一句提示打扰用户。

那条路没了之后，会走到选人弹窗的每一次调用都是用户刚刚明确表示要挂一个人，于是这个开关的值恒为 false。参数、分支与那句解释一并删除：`pickPerson(ctx, title)` 两个参数，库里没人时那句引导一律要说。留着一个只有一种取值的开关，下一个读代码的人得花时间确认它到底有没有第二种用法。

### 15.4 备案：这是 `create-project-moc.js` 移植纪律的第一次主动破例

modules/projects 的 L2 写着「其余逻辑连同守卫与错误文案原样保留」。本次改动破了它，理由记在这里：原脚本那两个选项在 QuickAdd 里是同一套问答的两个分支，移植时逐字保留是对的；但把它放进插件、放到零基础学员面前之后，「靠 Esc 表达确认」这件事的成本才暴露出来。破例的边界很窄——只动归属这一屏的选项数量与是否追问，名称校验、防覆盖、光标落点、错误文案一字未改。

### 15.5 验收

1. 「新建项目」→ 选「自己做」：**不再弹选人**，直接问概述。建出来的 MOC 里既没有 `client` 也没有 `with`。
2. 选「和别人一起做」→ 选张三：MOC 里是 `with: "[[张三]]"`，导航页与客户表都不把它当客户。
3. 选「和别人一起做」→ 按 Esc 不选人：项目照样建出来，只是不带 `with`。
4. 选「客户委托的」→ 按 Esc 不选人：提示「未选择客户，操作已取消。」，且**不留任何文件夹**。
5. 空库（一个人脉档案都没有）选「客户委托的」：弹一句「还没有任何人脉或客户档案……」，然后按第 4 条中止。
6. 打开张三的人脉档案：第 2 步那个项目出现在「相关项目」里（这一条验的是 `with` 仍被读取）。
7. 开荒的首个项目仍免问答，一次弹窗都不弹。

## 16. 作者名片（v0.9.0）

### 16.1 动机与形态

插件会脱离仓库单独流传，而 `main.js` 是唯一一定跟着走的文件。作者的入口因此必须编译进插件本体，而不是只写在 README 或某篇笔记里——那两样都可能被删、被略过。传播本身于是变成获客：谁拿到插件，谁就看得到作者是谁、去哪找他。

内容三层，全部住在 `src/modules/about/view.ts` 一个文件里（改链接只改这里）：

| 层 | 内容 | 展示形态 |
|---|---|---|
| 站点 | 官网 `zhaozimin.cn` / `zhaozimin.com`；插件教程 `edu.zhaozimin.cn` / `edu.zhaozimin.com` | 文字链接，双域名并列，后缀注明（大陆）/（海外），下面一行小字解释 .cn 部署在中国大陆、.com 部署在海外 |
| 开源 | GitHub `github.com/zhaozimin`（更多开源工具） | 品牌 logo 胶囊按钮 |
| 自媒体 | X `x.com/ZiminZhao`、YouTube `youtube.com/@ZiminZhao`、B站 `b23.tv/E2UTPzQ`、小红书 `xhslink.cn/m/3NnLHIc6lQA` | 品牌 logo 胶囊按钮，X 与 YouTube 的 @ 手柄已转成可点击跳转的完整链接 |

**除官网与插件教程外，其余入口一律用官方品牌 logo 显示**（产品要求）。图形取自 Simple Icons（CC0，`simple-icons@15`，见 docs/第三方组件.md）：GitHub 与 X 的官方标就是黑白两版，取 `currentColor` 随主题走；YouTube/B站/小红书按品牌色显示，品牌色作为数据写在元素上而不进 styles.css。

### 16.2 两个挂载位

同一个 `renderAboutPanel` 挂两处，覆盖两条传播路径：

1. **首页导航尾部**：第二十二个视图「关于作者」。`navContent()` 在 base 块之后追加一条分隔线与 ` ```ziminos 关于作者 ``` ` 块——块里只有视图名，画什么由 main.js 决定，名片随插件升级而更新，不随建库时那篇笔记冻结。视图名 `ABOUT_VIEW` 住在 core/constants：它是唯一被两个模块（about 定义、projects 引用）共用的视图名，写成两处字面量的话改一处就静默失联。
2. **设置页第十张标签页「关于」**：经 `SettingActions` 新增的 `renderAbout` 洞注入（设置页不 import 模块的纪律不破）。它落成一张页而不是塞进某页页尾，是 §12 那条同名纪律的必然结果——名片住在 `modules/about/`，分页就该有 `about` 这一张；它也是十张里唯一没有设置项的一页，页头那句改为回答「这套东西是谁做的」。没开过荒、或把 main.js 单独拷进旧库的用户，打开设置页也看得到。

已有库升级的边界：开荒补齐不改写已存在的导航页，因此老库的导航页尾不会自动长出这个块——设置页那一份保证了名片仍然可见；学员愿意的话，在任何笔记里手写同名代码块即可得到同一张名片。

### 16.3 纪律自查

- 零网络请求：五段 logo path 是编译期常量，渲染不发任何请求；链接点击由系统浏览器打开，是用户动作。
- 人主导：名片是静态展示，无任何写入。
- 公开 API：DOM 由 `createEl`/`createSvg` 构建，均为 obsidian.d.ts 公开辅助；不新增红线偏离。

### 16.4 验收

1. 全新库开荒后打开「导航」：底部分隔线下出现名片——两行站点（各带大陆/海外两个链接）、一行小字解释、五个带 logo 的胶囊按钮。
2. 逐个点五个按钮：GitHub/X/YouTube/B站/小红书 各自在系统浏览器打开对应账号页；X 与 YouTube 落在 `x.com/ZiminZhao` 与 `youtube.com/@ZiminZhao`。
3. 切换明暗主题：GitHub 与 X 的 logo 颜色跟随正文色；YouTube 恒红、B站恒蓝、小红书恒红。
4. 设置 → ziminOS 拉到最底：「关于作者」区显示同一张名片。
5. 手机端窄屏：五个按钮自动换行，不撑破页面。
6. 删掉导航页里的那个代码块：其余视图零影响；在任意笔记里重写该块，名片重新出现。
